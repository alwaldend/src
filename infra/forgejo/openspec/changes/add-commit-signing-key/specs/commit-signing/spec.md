## Purpose

Preserve a Vault-backed instance identity for commits generated by Forgejo,
including merges and file edits, across repeated infrastructure deployments.

## ADDED Requirements

### Requirement: Durable instance signing identity

Setup SHALL generate a dedicated Ed25519 SSH signing pair once and store it in
the Forgejo AppRole's Vault KV namespace. Secret values MUST NOT appear in Git,
Terraform state, process arguments, or command output. Repeated bootstrap SHALL
reuse a valid matching pair and SHALL NOT overwrite an existing record.

#### Scenario: Repeat bootstrap

- **WHEN** setup is explicitly repeated with an existing valid Vault record
- **THEN** its signing identity remains unchanged

#### Scenario: Unusable existing cache

- **WHEN** cache access fails or existing data/history is incomplete or corrupt
- **THEN** bootstrap fails without generating or overwriting the stored identity

### Requirement: Deploy the cached signing identity before activation

Ansible SHALL install the cached pair with service-only private-key access before
activating Forgejo. The instance SHALL use SSH signing with explicit name and
email, retaining the existing merge, CRUD, and trust policies. Deployment SHALL
reject a different existing private key instead of rotating it implicitly.

#### Scenario: Sign an instance-generated commit

- **WHEN** Forgejo creates a file-edit commit with the deployed configuration
- **THEN** the commit has a verifiable SSH signature from the cached identity

#### Scenario: Repeat deployment

- **WHEN** the same pair and configuration are deployed again
- **THEN** private content remains unchanged and no key rotation is performed
