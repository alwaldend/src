## Context

See proposal.md for scope. The worktree is
`t3/restrict-bazel-dependency-trees`; its existing Bazel pin is 9.3.1.
Root MODULE.bazel is generated by `tools/bazel_module/cmd/update/main.go`.
`tools/gazelle` owns the language registry. Existing standalone extensions
provide the module and integration pattern.

## Goals / Non-Goals

Generate package policy from explicit TOML path mappings, preserve unrelated
BUILD declarations, and enforce the generated restrictions during analysis.
The plugin does not infer policy from directory names or interpret README
prose. Host configuration and infrastructure deployment are excluded.
The user's artifact-boundary requirement excludes Starlark loads and
execution-tool/toolchain edges. Native package policies cannot express all
of those edge-specific exemptions; document that limit and exclude execution
tools when querying ordinary artifact dependencies.

## Decisions

Decision review: **proceed** with the requested configuration-driven generator.
Hand-editing every package does not provide maintainable inheritance, and a
query-only check does not supply the requested native analysis failures.

- Use the explicitly requested project path and a self-contained Bzlmod module.
  Reuse the repository's Gazelle 0.54.0 and rules_go 0.60.0 dependencies.
- Read `tools/transitive_visibility/transitive_visibility.toml` in the selected
  workspace. Its `[paths]` table maps canonical workspace-relative directory
  paths (`"."` for the root) to absolute package-group labels. The longest
  directory-prefix match wins; sibling names do not match accidentally.
- Provide `-transitive_visibility_config` for standalone consumers. Relative
  config paths resolve from Gazelle's repository root. An absent default file
  leaves policy unmanaged; an explicitly selected missing file fails. Never
  search parent workspaces. Reuse the existing BurntSushi/toml 1.5.0 parser.
- Validate the entire configuration before writing files. Reject unknown fields,
  malformed TOML, invalid paths, empty mappings, and relative or invalid labels.
  Reject obsolete BUILD directives with a migration diagnostic.
- The configuration owns only the `transitive_visibility` package attribute.
  Without a matching path, preserve manual policy. Preserve unrelated attributes
  and comments; do not create empty packages solely for policy. Place managed
  package declarations after loads and before rules in existing BUILD files.
- Keep the shared repository flag in checked-in Bazel configuration. Update
  first-party module compatibility to the pinned Bazel 9.3.1 baseline, including
  the root generator's authoritative header.
- Keep policy groups in their owning trees. Preserve the documented website
  documentation and developer/test exceptions, as selected by the user.
  Do not allow the Ansible project's infrastructure certificate dependency.
  Public trust material may instead be owned by data and consumed from there.

### Declaration ordering

The user requires unmodified upstream Gazelle and authorizes upgrading it first.
Use stable Gazelle 0.54.0 in the root and plugin workspaces. Repair existing
package ordering through the extension's normal APIs. The real-Gazelle fixture confirms that 0.54.0 still appends package declarations
in newly created files. Preserve and document that behavior; a later generation
repairs ordering. Do not patch Gazelle or introduce a post-generation rewrite.

Full-language generation exposes unrelated Go/Python and skill rule drift,
including duplicate Python target names and removal of generated WASM inputs.
Preserve those hand-maintained rules. Regenerate and check idempotence with
`-lang=enforce_transitive_visibility`; repairing other generators is outside
this policy migration.

### Public certificate ownership

The user selected separate Terraform roots under `data/ssh/tf` and
`data/ssl/alwaldend.com/tf`. Move the existing four public snapshots without
changing their bytes; data BUILD targets reference local files. Refresh roots
read public values through Vault data sources and manage only their local output files. They do
not read infrastructure state or use infrastructure BUILD targets. Normal
project builds consume checked-in snapshots and never perform a refresh.

Remove the four `local_file` exports from `infra/vault/tf`, using `removed`
blocks with `destroy = false` so a later authorized apply relinquishes old
state ownership without deleting files. Update path consumers as well as
Bazel labels. Reuse the pinned Vault 5.8.0 and Local 2.9.0 providers. The
`vault_generic_secret` data source reads JSON from PKI `cert/ca` and SSH
`config/ca` endpoints. No HTTP provider, custom downloader, or KV copy is
needed. Shared AL configuration supplies the operator's existing credentials.
An explicit absolute output directory avoids runfiles-only updates, and each
root uses a separate local backend path under ignored `out/`, supplied through
the existing launcher backend-configuration environment variable.

Use native Terraform formatting and schema validation plus Bazel packaging and
dependency queries. The user declined a custom integration harness for this
standard Terraform usage. Check the unchanged snapshot hashes, configured
read paths and output filenames, and absence of infra targets in the
collection's complete dependency query. Live refresh and operational access
are not verified or performed in this task.

## Risks / Trade-offs

The complete external dependency query exposed a stale Python alias and the
retired downloader container's Alpine pull. The user authorized removal of
unused declarations. Repository reference inspection found no requirements
alias consumers. The only Alpine consumer is the downloader's go_oci target
and its Harbor-only build test; published releases use the standalone binary.
Remove that container path and the Alpine owner, retaining the binary, tar,
cross-build and release targets. Python dependencies continue to use the native
uv.lock owner without replacement requirements exports.

The requested root-only and external-inclusive diagram variants are task
artifacts under ignored out/. Keep individual targets, full labels and unlimited
depth, with no package grouping. Export dark WebP variants using pinned
visualization dependencies and the site's dark diagram palette. Raster
overviews retain every target and edge but use sparse annotations; the
companion Mermaid files retain every full label. Do not commit captures,
diagram sources or rendered artifacts.

The user authorized repairing the remaining Gradle validation blocker. The
wrapper indexes the first file of the deprecated Bazel shell-runfiles target,
whose default file set is empty. Reuse the existing rules_shell runtime and
merge its default runfiles and declared files, following the packaged-binary
rule's existing pattern. Check both analysis and execution: the shell library,
pinned Gradle distribution, and selected Java runtime must all resolve without
runtime downloads. Keep caches under ignored task scratch.
The version check also exposed a stale hardcoded Gradle repository name. Derive
the launch paths from the declared Gradle file and Java toolchain provider,
normalizing their workspace-relative runfile paths instead of copying Bazel's
generated external repository names into source.

The user also authorized fixing the stale `bzlenv` labels discovered by
delivery lint. Use the existing repository-visible binary targets for Blender,
Buf, DNSControl, Hugo, Minisign, ORAS, ShellCheck, and Taplo in `third_party`.
Keep repository-owned tools under `tools` and preserve the selected tools;
this needs no dependency changes or new compatibility aliases.
The old environment added executable directories to PATH and ignored the map's
command names. Migrated wrappers have filenames such as
`hugo_native_binary.exe`, so successful analysis alone does not restore `hugo`.
Expose the configured names as runfiles symlinks in a dedicated tool directory
and retain each executable's runtime files. Verify command resolution and
non-mutating version commands in an isolated environment without a repository
`.env` file.

- Package policy cannot distinguish tests, documentation, and production
  targets sharing a package. Record the selected exception policy explicitly;
  do not present tree policy as complete enforcement of all README rules.
- Enabling enforcement exposes existing violations. Preserve analysis
  diagnostics and report policy failures separately from generator defects.
- Generated BUILD churn can conceal unrelated changes. Inspect the first
  generation, require an unchanged second generation, and use the configured
  formatter rather than editing generated declarations manually.

## Validation failure cases

Before implementation, cover missing configuration, longest-prefix selection,
sibling isolation, malformed and unknown fields, invalid paths and labels,
explicitly missing files, existing package attributes and comments, BUILD and
BUILD.bazel, newly generated packages, empty directories, nested workspaces,
existing-file ordering, upstream new-file ordering, and idempotence through the real Gazelle executable.
Preserve observable generated artifacts. The existing native enforcement fixture
remains evidence for direct rejection and the documented indirect limitation.

## Migration Plan

Runtime finding: an isolated Bazel 9.3.1 fixture rejects a direct rule and
source-file consumer, and rejects an indirect consumer when the intermediary
has no local declaration. The same indirect consumer succeeds when the
intermediary declares a permissive group. Preserve this failed acceptance
evidence; do not claim complete indirect enforcement. The requested generator
continues to emit the specified label without inventing a second policy engine.

The versioned implementation accumulates `PackageSpecificationProvider`
instances in an `ImmutableSet`. Their inherited `NativeInfo.equals` compares
Starlark fields, while package specifications are not exposed as fields. This
appears to collapse distinct restrictions and retain the first (local) one.
That root-cause interpretation is source-based; the behavioral discrepancy was
reproduced with the pinned executable.

Implement and validate the plugin first; register it, update compatibility and
repository configuration, generate tree declarations, then inspect and validate
the resulting dependency boundaries. Finish repository delivery only after
recording all validation results and outstanding policy violations.
