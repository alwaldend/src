This deployment runs OpenStack on two CentOS Stream 10 bare-metal hosts.

```text
master1.openstack.alwaldend.com  192.168.1.2
  OpenStack control plane, OVN gateway, Glance, and Cinder
  SATA RAID1 -> cinder-fast
  DAS RAID10 -> cinder-bulk

compute1.openstack.alwaldend.com 192.168.1.3
  Nova compute, libvirt, OVN controller, and agent instances
  dedicated 2 TB NVMe mounted at /var/lib/nova

openstack.alwaldend.com          192.168.1.4
  Kolla internal and external API VIP
```

The MikroTik DHCP pool starts at `192.168.1.10`, so these three addresses are
kept outside the dynamic pool.

## Configuration

Edit [`ansible/inventory.yaml`](./ansible/inventory.yaml):

- Replace the two `openstack_mac_address` values.
- Replace the network-interface placeholders.
- Replace the storage `/dev/disk/by-id/...` placeholders.

The inventory is the source of truth for the master and compute addresses.
[`kolla/globals.yml`](./kolla/globals.yml) is the source of truth for the API
VIP. The MikroTik Terraform package reads both files.

## Vault

Apply the Vault Terraform change first:

```sh
bazel run //infra/vault/tf:tf.plan
bazel run //infra/vault/tf:tf.apply
```

It creates the `src_infra_openstack` AppRole and the
`src_infra_openstack_ssh` SSH host-certificate role for
`openstack.alwaldend.com`.

Add these KV secrets below the `secrets` mount:

```text
alwaldend.com/vault1/approles/src_infra_openstack/kolla
  passwords_yml

alwaldend.com/vault1/approles/src_infra_openstack/mikrotik
  mikrotik_username
  mikrotik_password
```

`passwords_yml` is the complete Kolla `passwords.yml` document generated by
`kolla-genpwd`.

The Terraform HTTP backend stores its state and lock automatically below:

```text
alwaldend.com/vault1/approles/src_infra_openstack/tf_backend/tf
```

No backend KV value needs to be initialized manually.

## MikroTik

Plan and apply the static DHCP leases and DNS records:

```sh
bazel run //infra/openstack/tf:tf.plan
bazel run //infra/openstack/tf:tf.apply
```

Terraform creates these records on RouterOS:

```text
master1.openstack.alwaldend.com  -> 192.168.1.2
compute1.openstack.alwaldend.com -> 192.168.1.3
openstack.alwaldend.com          -> 192.168.1.4
```

## Host storage

The repository Ansible target always manages storage. There are no storage
feature toggles.

```sh
bazel run //infra/openstack/ansible
```

It creates:

```text
master:
  2 SATA SSDs -> /dev/md/cinder-fast -> VG cinder-fast
  4 DAS HDDs  -> /dev/md/cinder-bulk -> VG cinder-bulk

compute:
  dedicated NVMe -> XFS -> /var/lib/nova
```

Verify every `/dev/disk/by-id/...` path before running the target. The target
creates RAID arrays, LVM volume groups, and the compute filesystem when they do
not already exist.

## Kolla-Ansible

The deployment machine must have a compatible `kolla-ansible` executable in
`PATH`.

Run Kolla's dependency installation and deployment stages as separate Bazel
targets:

```sh
bazel run //infra/openstack/kolla:kolla.install_deps
bazel run //infra/openstack/kolla:kolla.bootstrap_servers
bazel run //infra/openstack/kolla:kolla.prechecks
bazel run //infra/openstack/kolla:kolla.deploy
bazel run //infra/openstack/kolla:kolla.post_deploy
```

Apply later configuration changes with:

```sh
bazel run //infra/openstack/kolla:kolla.reconfigure
```

The Kolla target uses the same YAML inventory as the repository Ansible target.

## Storage layout

Nova stores VM roots, ephemeral disks, image caches, and agent workspaces below
`/var/lib/nova/instances` on the compute NVMe.

Use the `fast` Cinder backend for persistent latency-sensitive data and the
`bulk` backend for larger persistent data. The 1 GbE link remains the limit for
remote Cinder I/O.

RAID protects against some disk failures. It is not a backup.
