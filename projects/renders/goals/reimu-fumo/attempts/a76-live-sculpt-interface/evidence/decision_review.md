# A76 adversarial strategy review

## Recommendation

**REJECT the proposed live-MCP sculpt-interface probe as the next attempt.**
It is not a materially new interface: A68 already used the repository-pinned
Blender 5.2.1 in a foreground `VIEW_3D` through the interactive MCP bridge,
split setup and stroke across settled MCP calls, invoked the native Essentials
Grab brush, and measured the resulting coordinates. A71 repeated the same
foreground/live-context method on fresh uniform topology in Blender 5.1.1.
Both operators returned `FINISHED`; both failed because their useful support
was tiny or visually became local dents. The current Blender MCP exposes code
execution and screenshots, but no distinct pointer-event sculpt tool. Calling
`bpy.ops.sculpt.brush_stroke` through it again changes transport state, not the
authoring method.

**PROCEED instead with a small direct BMesh/proportional-edit macro-form
probe, then expand it only after fixed-view pixels improve.** This is a
recommendation to the primary agent, which retains ownership of the final
decision. Use the A52 masks only as outer-envelope veto evidence; defer the
226-vertex face carrier; and do not build another A70/A74 panel family.

## Actual outcome and constraints

The outcome is not merely a technically editable mesh. It is a reusable,
animatable Reimu Fumo whose complete front, profiles, rear, and both
three-quarter views read as the supplied sewn plush. The protected rung and
tracked asset must remain byte-identical until a disposable candidate passes.
Every next method must therefore produce a visible whole-head/hair improvement
in full-plush context, not only a topology or operator-success result.

The dominant unresolved defect is the coupled head/hair macro-form: the current
model reads as a deep hard helmet with generic panels. The exposed beige face
is secondary. A75 measured that only `27.73%` of the receiver is visible from
the front, about `16%` in either three-quarter, `3.56%` in profile, and `0%`
in rear; changing it alone cannot repair the crown, side, rear, or hair roots.

## Strongest case for the live-MCP proposal

Sculpting is artistically appropriate for low-frequency stuffed forms, and a
foreground viewport can in principle provide feedback that analytic builders
lack. A tiny, disposable support test would be cheap and reversible. If the
current MCP provided real pointer events distinct from Python-constructed
stroke records, it could test whether the earlier failures came from synthetic
operator invocation rather than Blender sculpting itself.

That is not the capability presently exposed. The available mutation path is
`execute_blender_code`, which invokes the same `bpy.ops.sculpt.brush_stroke`
path already tested.

## Strongest reason live MCP sculpt can still fail

It has already passed as an interface and failed as a useful modeling control.
The novelty claim in the A76 plan is contradicted by direct evidence:

- A68's foreground report records pinned Blender 5.2.1, the interactive MCP
  bridge, a real live `VIEW_3D`, separate settled calls, an exact Essentials
  Grab asset, `poll == true`, and `FINISHED`. Its production C1 moved only 35
  vertices. C2 used 420 px brushes and moved the same 35 vertices on each
  side by as much as `8.36 mm`; the pixels became paired dimples, not a broad
  head correction. Overall likeness was `5/10`, macro silhouette `4/10`, and
  construction `3/10`.
- A71 did not use a background-only synthetic path. Its scripts explicitly
  require non-background Blender 5.1.1, a live `VIEW_3D`, separated MCP calls,
  and a scene-locked `50 mm` radius. Ordinary Grab moved 11 of 3,863 vertices
  (`0.285%`). Elastic Grab changed floating-point coordinates globally but
  moved only 40 vertices more than `0.10 mm`; its maximum was `0.814 mm`.
  Fresh uniform topology therefore did not cure useful support.
- A11 had already found that changing VIEW/SCENE locking, requested size
  `95/150/540`, scene radius `0.22/1.0`, and view distance did not expand the
  ordinary Grab neighborhood beyond four vertices.

Thus another MCP call can easily satisfy operator, context, and save/reopen
checks while producing no controllable macro-form. The likely failure is not
that MCP cannot reach Sculpt mode; it is that a code-authored native stroke is
not a usable broad art-direction primitive in this setup. Calling it "live"
does not supply the missing human visual gesture loop.

## Exact reversible discriminator

There is no new discriminator using the current Blender MCP surface because
it has no viewport pointer/drag tool; all geometry mutation returns to Python
code and the already-tested operator. The read-only capability check is enough
to reject the claim that A76 is materially different.

If a genuinely distinct GUI-event route becomes available later, test it as
follows and do not call `bpy.ops.sculpt.brush_stroke` from code:

1. Open the immutable A71 raw uniform macro-clay artifact in a disposable
   foreground process and duplicate the target as a single-user object.
2. Select Sculpt mode and the exact Essentials Grab asset with a world-locked
   `50 mm` radius. Use one real pointer drag at the same audited rear-upper
   surface point for a `4 mm` intended displacement.
3. Use Python only after the pointer event to measure coordinates. Require at
   least `8%` of vertices to move more than `0.10 mm`, at least `1%` to move
   more than `0.50 mm`, one connected support region spanning at least
   `60 mm` in both head-height and head-width directions, and a maximum below
   `6 mm`.
4. Render a clay side and three-quarter A/B. Reject if the edit is a dimple,
   has a hard curvature ring, or changes fewer than `1%` of pixels by more
   than one percent RGB. Verify the source hash and discard the copy.

Passing that test would reopen live sculpting. With the present tools, it
cannot be run differently from A68/A71 and should not consume an attempt.

## Revised next probe

This recommendation does **not** mean repeating A56A's dense 10,242-vertex
icosphere plus scripted `broad_plane_brush`, `vector_grab_brush`, and
`pinch_brush` fields. That was already rejected as a rounded foam block or
upright mattress, with construction, side/gusset, and bottom closure all at
`2/10`. It also does not mean independently deforming the legacy seven-object
stack; A69 showed that route trades small silhouette motion against lost
attachment while preserving the helmet representation.

Do not start another full head rebuild. Create one fresh disposable macro
blockout with low enough control density that every moved region is auditable.
Use standard BMesh/Edit-mode selection plus proportional transforms to author
four observed low-frequency facts only: broad shallow face plane, compact
crown, high rear fullness, and lower-rear turn-in. Do not derive all vertices
from a superellipsoid, loft, visual hull, or per-height formula, and do not
touch the dense legacy helmet.

Judge the first checkpoint in full-plush context with the current bow/body as
witnesses but no detailed new hair panels. Require front, side, and the worse
three-quarter view to be visibly preferred to rung 003 and to avoid sphere,
egg, mattress, helmet, card, or anatomical-head reads. Stop after that packet
if macro silhouette or plush construction is below `6/10`. Only a passing
macro surface earns separate padded hair retopology; the A52 guide may veto
gross extent, and the 226-vertex face carrier may be revisited after the hair
opening and carrier interface are no longer frozen to rejected geometry.
