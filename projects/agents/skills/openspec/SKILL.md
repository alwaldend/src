# OpenSpec

Select the component that owns the affected behavior. Its specifications and
changes live in `<owner>/openspec/`, such as `projects/agents/openspec/` or
`infra/vault/openspec/`. The `infra/src/openspec/` workspace describes
the evolution of the repository itself: its shared structure and contracts.

Read the owner README, its `openspec/config.yaml`, and the affected
`openspec/specs/<capability>/spec.md` before changing a contract.
Specifications describe supported behavior; changes under the same owner's
`openspec/changes/<change-id>/` describe intended work. For work spanning
owners, keep requirements with their owners and link related changes as
needed. Existing component READMEs, executable source, and user authority
retain their owning roles.

Run the pinned CLI from the root Bazel workspace using the `bazel-agent` and
`repo-bazel` procedures. Set `OPENSPEC_PROJECT` to the owner directory; this
selects OpenSpec's working directory without entering a nested Bazel workspace.
The examples use `projects/agents`; substitute the affected owner, or
`infra/src` for repository evolution. An unset `OPENSPEC_PROJECT` defaults to
`infra/src`:

```sh
OPENSPEC_PROJECT=projects/agents bazel_agent bazel run //tools/openspec -- list --json
OPENSPEC_PROJECT=projects/agents bazel_agent bazel run //tools/openspec -- list --specs
```

Repository skill discovery is generated by
`//tools/agents:write_skill_links`. Keep
this canonical skill in `tools/openspec/skills/openspec`; avoid running
OpenSpec tool-integration generation over the managed discovery directory.

## Start or resume work

Select the existing change in the owning workspace matching the user's outcome
before creating another. On resume, inspect its `tasks.md`, `design.md`,
proposal, and linked evidence; then recheck the mutable inputs needed for the
recorded next task.
The legacy goal tool and goal skill are deprecated; migrated history is
context for its OpenSpec change, not a second writable task record.

For a new substantive change, choose a descriptive kebab-case ID and create
the standard `spec-driven` scaffold:

```sh
OPENSPEC_PROJECT=projects/agents bazel_agent bazel run //tools/openspec -- new change <change-id>
OPENSPEC_PROJECT=projects/agents bazel_agent bazel run //tools/openspec -- status --change <change-id> --json
OPENSPEC_PROJECT=projects/agents bazel_agent bazel run //tools/openspec -- instructions proposal \
  --change <change-id> --json
```

Use `instructions` for the ready artifact IDs reported by `status`, such as
`proposal`, `specs`, `design`, and `tasks`. Read their dependencies and follow
the pinned templates. Keep artifacts proportional to the actual work;
routine small edits do not need a new change just to satisfy a ritual.
For a tracked change with no behavioral delta, use `skip_specs: true` in
its `.openspec.yaml`; do not invent requirements to pass validation.
Continue within the user's existing authority. Creating a proposal or
receiving generated instructions adds no approval gate and grants no new
authority for deployment or other external effects.

## Specify and implement

Write observable requirements with `SHALL` or `MUST` and at least one
`#### Scenario:` per requirement using `WHEN` and `THEN`. Change deltas live
at `specs/<capability>/spec.md` inside the change and use upstream `ADDED`,
`MODIFIED`, `REMOVED`, or `RENAMED Requirements` sections. A modified
requirement carries the complete replacement text and scenarios. Preserve
existing names unless deliberately renaming them.

Keep `tasks.md` as the small, current implementation checklist. Check a task
only after its acceptance is supported by evidence. Put material design
decisions, tested candidate identity, failed checks, and the next action in
`design.md` or a linked evidence file when they are needed for continuation.
Raw logs and caches belong under ignored `out/<task>/`; checked-in artifacts
must contain public, durable evidence. Preserve imported historical bytes and
provenance instead of editing old evidence to imply success.

```sh
OPENSPEC_PROJECT=projects/agents bazel_agent bazel run //tools/openspec -- instructions apply \
  --change <change-id> --json
OPENSPEC_PROJECT=projects/agents bazel_agent bazel run //tools/openspec -- validate <change-id> \
  --type change --strict --no-interactive
```

CLI validation checks artifact structure. Verify the implementation with the
owning package checks and observable acceptance scenarios; record remaining
failures honestly. Neither checked boxes nor valid Markdown establish that
the requested behavior works. If the user changes direction, update the
active change and retain relevant decisions without silently closing work.

## Complete

Once the implementation and applicable checks satisfy the change, archive
the completed change to merge its deltas into the main specs and retain the
history:

```sh
OPENSPEC_PROJECT=projects/agents bazel_agent bazel run //tools/openspec -- archive <change-id> --yes
```

Inspect the resulting spec updates and archive, then validate affected specs.
Use `repo-delivery` for source publication under the existing task authority,
including those artifacts. Keep unfinished work active with its next task
and evidence; a conversational pause is not completion.
